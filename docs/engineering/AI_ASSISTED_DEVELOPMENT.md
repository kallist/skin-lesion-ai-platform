# AI-assisted Development

这份文档记录本项目**如何使用 AI Coding Agent 完成工程开发**，以及这套做法在哪里有效、
在哪里必须由人接管。它不是「让 AI 写了一个项目」的记录，而是把 Agent 当作工程流程中的一个执行环节
之后，如何保证交付质量的过程说明。

## Problem Definition

Agent 无法替人决定「做什么」，也无法替人承担「做错了」的后果，因此每个阶段都由人先定义：

- **Goal**：这一阶段要交付什么可验证的结果（例如「上传→推理→返回倾向」的端到端链路可用）。
- **Non-goals**：明确不做的事，避免 Agent 自行扩张范围（例如不做多模型集成、不做用户反馈系统、
  不为了让指标好看而调整阈值或重新训练）。
- **Scope**：本次改动的边界（哪些目录、哪些接口、是否允许改数据库 schema、是否允许改 API 契约）。
- **Acceptance Criteria**：可判定的完成条件（测试数量与结果、真实运行验证方式、指标必须来自 artifact）。

这些定义先于任何代码生成，并在评审阶段被用来判断「是否真的完成了」。

## Engineering Prompt

交给 Agent 的不是一句话需求，而是一份结构化说明，固定包含以下几类约束：

| 类别 | 写入提示词的内容 |
| --- | --- |
| 架构约束 | 分层与依赖方向（API → services → repositories/DB；DetectionService → ModelService → PyTorch）、允许新增什么、禁止改什么（API 路径、数据库表结构、模型 artifact） |
| 安全要求 | 口令哈希、会话与 Cookie、CSRF、越权访问、图像加密、EXIF 剥离、日志脱敏、上传防护，逐条要求「实现 + 有测试」 |
| 并发与失败处理 | 模型单例与加载时机、并发上限与超时、上传幂等、事务边界、孤儿文件清理、统一错误契约 |
| 测试要求 | 每个安全/管线要求都要有对应测试；端到端测试必须走真实后端；前端要有类型检查与构建 |
| 验收标准 | 明确写出「什么算完成」：例如测试全绿、模型 SHA256 不变、指标与 artifact 一致、真实运行截图可用 |
| 诚实性要求 | 禁止虚报指标、禁止把未实测的东西写成已验证、禁止出现「临床级」等医疗过度表述 |

提示词模板留在仓库中（`docs/prompts/`），可复用技能说明在 `skills/skin-lesion-ai-webapp/SKILL.md`。

## Agent Execution

Agent 在以下环节承担了主要工作量：

- **repository audit**：遍历仓库结构、依赖、脚本与文档，列出真实状态与不一致之处；
- **implementation**：按约束实现前后端功能、安全控制与错误处理；
- **tests**：补齐 pytest / Vitest / Playwright 用例，并让它们真实运行；
- **documentation**：产出架构、接口、数据库、测试与部署文档；
- **refactor & migration**：例如把文档目录重组为作品集结构，并自动重写上百处相对链接。

明确由人保留的判断：需求取舍、验收标准、指标口径、是否重新训练、任何对外表述。

## One Worked Example of the Loop

评审与修正的价值在小事上最容易看清。下面这条记录来自 `docs/testing/TEST_REPORT.md` §10
（失败与修复记录），它是「Agent 产出 → 人发现问题 → 修改 → 测试锁定」的一个完整回合：

| 环节 | 内容 |
| --- | --- |
| Agent 的产出 | 数据审计里用 `aHash` 做近似重复检测，并在文档里表述为"已实现近重复聚类" |
| 人的发现 | 检查聚类结果时发现一个泄漏组里塞进了 **289 张互不相关的图片**——`aHash` 对这类图像过粗，把不同病灶混成一组 |
| 判断 | 这不是"文档措辞问题"，而是会直接影响划分正确性的实现缺陷（组划分错了，泄漏断言就失去意义） |
| 修改 | 换成 `dHash`，并且把近重复聚类**限制在同一类别内**，避免把不同类别的病灶强行并组 |
| 回归 | `backend/tests/test_ml_pipeline.py` 增加/保留了划分无泄漏与完整性校验用例；后续划分结果三重交集为 0 |
| 留下的记录 | 该条已写入测试报告的失败与修复表，并在 `ml/dataset.py` 中可见（dHash 实现 + 类别内聚类） |

同类被记录下来的还有**声明类**问题：文档里出现过引用不存在的 npm 脚本、把近重复算法名写错、
把未实测项写成已验证等表述，都是在 claim audit 环节被逐条对照代码后改掉的。
这也解释了为什么本文档的立场是「**Agent 的输出不视为完成**」——不是不信任工具，
而是这类错误只有靠对照代码与运行结果才能发现。

## Human Validation

**Agent 的输出不视为完成。** 每一轮产出都经过下面这类验证才被接受：

1. **code review**：逐文件读 diff，检查安全边界与契约是否被破坏（例如上传接口是否真的强制 CSRF）。
2. **test execution**：真的把测试跑起来看结果，而不是相信「应该会通过」；后端 106 项、前端 37 项、
   端到端 5 用例 × 4 浏览器都是本地实跑结果。
3. **runtime verification**：启动真实服务，用真实图片走一遍上传→推理→历史→对比→导出；
   并用真实模型冒烟脚本比对 API 与本地前向的概率差（< 1e-4）。
4. **metrics validation**：所有对外数字回到 `artifacts/` 复核，并保留复核脚本；
   模型权重在改动前后做 SHA256 对比。
5. **claim audit**：专门审计「文档里写了、代码里没有」的声明，把不成立的表述改掉
   （本项目确实查出过多条，例如不存在的 npm 脚本、被夸大的近似重复算法名、以及把未实测项写成已验证）。

## Independent Review

实际采用的迭代闭环是 **Implementation → Review → Fix → Regression → Acceptance**：

- 评审以固定角色进行（可复用的评审提示词见 `docs/prompts/REVIEW_PROMPT.md`），
  重点是找**缺陷与不实声明**，而不是复述实现；
- 评审发现的问题必须修掉并重新跑回归测试，才进入验收；
- 本项目历史上两轮独立评审发现了真实缺陷：检测上传接口缺少 CSRF 强制、模型加载失败时泄露模型路径，
  另有前端类型检查遗留与文档数字不一致等问题，均已修复；
- 交付前再做一次「数字与证据」交叉核对：文档数字一致性检查脚本（`scripts/check_final_numbers.py`）、
  前端评测页数值与 artifact 比对（`scripts/check_metrics_consistency.py`）、全仓相对链接检查
  （`scripts/check_links.py`）。

## What This Approach Does Not Do

- 不是自主软件开发系统：没有自动需求发现，没有自动验收，也没有自动发布；关键判断始终由人做出。
- 不能替代领域判断：模型选择、指标解释、医学安全表述、数据授权判断都由人负责。
- 会自信地产生错误声明：Agent 写出的文档里可能包含「测试通过」「已支持某能力」这类未经运行验证的内容，
  必须逐条回到代码与运行结果核对。
- 不会自动发现「不该做的事」：数据泄漏、医疗过度声明、越权访问这类问题需要在提示词里显式要求，
  并在评审中专项检查。

## Practical Rules Used Here

1. 先写 Non-goals，再让 Agent 动手；范围不清时 Agent 会自行扩张。
2. 任何安全与隐私要求都必须同时要求测试，否则容易只写成文档。
3. 指标只允许来自 artifact，禁止手抄；能写脚本比对的地方就写脚本。
4. 交付前的最后一步永远是「真实运行 + 复核数字」，而不是「文档写得完整」。
5. 对外表述遵循同一标准：说不清证据的事，就不写。
