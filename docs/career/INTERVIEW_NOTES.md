# Interview Notes

面试问答口径。所有数字与结论都能在仓库中核验（`artifacts/`、`models/model_meta.json`、
`docs/ml/`、`docs/testing/`）。回答里出现的边界（不是商业产品、不是医疗器械、外测未达标）
**不要省略**——这些正是这个项目最有说服力的部分。

## Q1 这个项目解决什么问题？

皮肤病变的外观差异很细微，普通人很难判断哪些皮损需要尽快就医。项目把「上传一张照片 →
得到一个良恶性倾向提示 → 留下可追踪的记录」做成了一条完整链路：数据处理与审计、模型训练与评估、
模型服务化、Web 产品化、安全与隐私、自动化测试、独立外部验证。

它解决的是 **AI 能力落成可用产品** 的问题，而不是再训练一个分类器：模型只是其中一环，
真正的工作量在服务化、权限、隐私、历史数据与质量保证上。

## Q2 你具体负责什么？

个人承担 AI 应用开发与产品设计全流程：需求与验收标准梳理、数据结构与划分方案、
ResNet50 训练与评估、FastAPI 服务化、React 前端实现、安全与隐私设计、自动化测试、
独立外部评测与文档交付。项目背景是校企联合 AI 应用实习实践项目，
由广州泰迪智能科技有限公司相关人员参与项目指导与实践。

## Q3 AI 在项目开发中怎么使用？

把 AI Coding Agent 纳入了工程流程，而不是让它替我决定做什么：

1. 人先定义 Goal / Non-goals / Scope / 验收标准；
2. 把架构约束、安全要求、并发与失败处理、测试要求、验收条件整理成结构化提示词（模板在 `docs/prompts/`）；
3. Agent 承担仓库审计、实现、测试补充与文档产出；
4. 产出必须经过代码审查、真实运行的测试、运行时验证与指标复核才被接受。

代价也要说清楚：Agent 会自信地写出「已支持 / 测试通过」这类未经运行验证的声明，
我实际审计出多条不实表述（例如引用了不存在的 npm 脚本、把 dHash 写成 aHash），都已修正。
所以流程里必须有一步「claim audit」。详见 `docs/engineering/AI_ASSISTED_DEVELOPMENT.md`。

## Q4 为什么选择 ResNet50？

三个理由：任务规模（1840 张、224×224、二分类）不需要更大容量；残差结构让 50 层网络训练稳定，
且 ImageNet 预训练权重在自然图像纹理上的迁移效果对本任务够用；推理成本可控
（单张 CPU 中位约 77 ms，参数约 2351 万），适合单机部署演示。

选型也做了可替换设计：`ml/model.py` 支持 resnet18/34/50/101，训练脚本用 `--model` 切换，
方便后续比较。

## Q5 内部测试为什么是 92.96%？

这是训练所用数据集内部留出的 270 张测试划分，只评估一次，模型选择完全走验证集（276 张），
早停在验证集 ROC-AUC 上触发。训练与评估使用同一套预处理。

但我会主动说明其中的乐观因素：数据集没有 patient_id / lesion_id，只能做图像级分组划分，
同一病灶的不同照片理论上仍可能分处不同集合。虽然做了重复图分组（SHA256 与 dHash ≤ 2 整组同划分）
把这种风险压到很低（三重交集断言为 0），但**它不等于患者级划分**，所以这个数字不能当作泛化结论。

## Q6 为什么外部只有 78.54%？

外部提供了一批与训练数据独立的 797 张图片（benign 400 / malignant 397），
用冻结模型一次性评测：Accuracy 78.54%、恶性召回 65.49%、Specificity 91.50%、ROC-AUC 0.9079，
没有达到训练阶段设定的 90% 目标。

我先排除了评估本身的问题：与训练/验证/内部测试集的 SHA256 重合为 0 / 0 / 0（无字节级泄漏），
评测脚本只做前向推理不含训练，指标由独立脚本从预测 CSV 重算并逐项比对通过（7/7）。

然后才是性能问题本身：**这就是真实的泛化水平**，比内部低 14.42 个百分点，我把这个结果完整保留，
没有针对测试集重新训练或调阈值。

## Q7 为什么恶性召回掉这么多？

外部测试上 Recall 从 93.97% 掉到 65.49%（−28.47 pt），137 例恶性样本被判为良性；
而 Specificity 基本不变（92.21% → 91.50%）。这说明不是简单的阈值偏移：如果只是阈值偏保守，
特异性会同步上升、准确率可以通过移动阈值找回来。

阈值扫描也支持这个判断。扫描里有两个常被引用的点：阈值降到 0.3 时外部准确率 80.93%
（README 里引用的是这个中间点），降到 0.05 时准确率 83.56% 但特异性掉到 77%
（两个数字都来自 `artifacts/external_test/threshold_sweep.json`，仅作分析、未应用到模型）。
也就是说：**召回是可以用阈值换回来的，但要付出大量误报的代价；
换不回来的是置信度本身**——Brier 与 ECE 同时变差（0.057 → 0.167、0.043 → 0.151）
说明模型在外部数据上不只判断偏移，置信度也失真了。

原因方面我必须诚实：**无法严格归因**。外部数据没有采集设备、患者来源、病灶级元数据，
我只能说数据分布差异是可能因素之一，不能断言「已证明是 domain shift」。
置信度失真（Brier/ECE 同时变差）也是未做概率校准的直接后果。

## Q8 怎么确认没有数据泄漏？

三重证据：

1. **划分层面**：把完全重复（SHA256 相同）与近似重复（dHash 距离 ≤ 2，同类别内）的图像
   用并查集聚成泄漏组，整组进同一个划分，然后在划分完成后断言 train/val/test 两两之间
   在 SHA256、组 key、类内文件名三个维度上的交集都为 0；
2. **外部评测层面**：对 797 张外部图片逐张计算 SHA256，与 train/val/test 清单比对，重合数为 0 / 0 / 0；
3. **训练流程层面**：训练循环只加载 train/val 清单，测试划分从不进入训练或调参路径
   （这在代码里是事实，不是注释声明）。

## Q9 为什么没有根据外部测试再调模型？

因为外部数据的角色是**检验**，不是调参。一旦用它选阈值、选模型或做微调，它就不再是独立证据，
78.54% 这个数字也就不再说明任何泛化能力。所以在评测前就冻结了权重与阈值，
评测后只做分析与记录：保留全部 171 条错误样本清单，把阈值扫描的结果归档但明确标注未应用。

如果将来要改进，应该引入新的独立数据，或用与外部数据同分布的**训练**数据重训
（外部测试集本身不能再作为测试集使用）。

## Q10 FastAPI 里的模型是怎么服务化的？

- **单例 + 启动加载**：`ModelService` 进程内单例，应用 lifespan 启动时加载一次权重，
  避免每个请求重复载入 94 MB 的模型；加载失败只对外暴露异常类型，不泄露路径。
- **共享预处理**：服务端与评估脚本调用同一个 `build_eval_transform()`，
  均值方差从 checkpoint payload 读回，杜绝训练/服务预处理漂移。
- **并发与超时**：`BoundedSemaphore(INFERENCE_CONCURRENCY)` 限制并发推理，
  获取超时 30s 返回可读的繁忙错误；阻塞的 forward 通过 `anyio.to_thread` 执行，不阻塞事件循环。
- **可观测性**：`/health` 同时返回数据库与模型状态，`/model/info` 返回模型版本、
  架构、输入尺寸、类别映射与校准状态；模型版本随每条检测记录落库并回传前端。

## Q11 图片为什么要加密？

皮肤图像属于敏感个人数据，而且用户上传的可能是身体隐私部位的照片。明文落盘意味着
任何拿到磁盘或备份的人都能直接看到原图，因此设计上做了三件事：

1. 上传后先真实解码，重新绘制像素并清空元数据（剥离 EXIF/ICC，避免地理位置等泄露）；
2. 用 Fernet 对称加密后落盘，密钥只通过环境变量注入，生产环境缺失密钥时应用拒绝启动；
3. 文件名由服务端生成（uuid4），文件名与路径都不可由客户端控制；读取时必须先做归属校验，
   只有本人通过授权后才能解密返回。

删除记录或删除账号时会同步删除密文，避免「记录没了但图片还在」。

## Q12 系统安全怎么做的？

按攻击面组织：

- **认证**：Argon2id 口令哈希（含恒定工作量比对，避免用户枚举的时序差异）；会话令牌只存 SHA-256 哈希；
  HttpOnly Cookie（`SameSite` / `Secure` 通过配置控制，生产需显式开启），登录尝试有滑动窗口限流。
- **授权**：所有读取、图片解密、删除的查询都强制带 `user_id` 条件，越权命中统一返回 404，
  不泄露「ID 存在但不属于你」。
- **CSRF**：非 HttpOnly 的 csrf_token + `X-CSRF-Token` 双重提交，上传、删除、改资料、删账号全部强制
  （这条正是第二轮独立评审发现缺失后补上的）。
- **上传**：真实解码校验（不信任扩展名与 MIME）、格式白名单、体积上限、
  像素与单边尺寸上限、路径穿越三层校验。
- **其他**：安全响应头、日志脱敏（口令/密钥/令牌/长 base64）。

已知边界我会主动说：限流只覆盖登录尝试，注册与推理端点没有配额（推理只有并发上限）；
`COOKIE_SECURE` 默认关闭，真实 HTTPS 环境未验证。

## Q13 这个项目最大的不足是什么？

模型泛化能力不足，而且影响是真实的：外部 797 张里 137 例恶性被判为良性。
在筛查语境下漏检的代价高于误报，所以这是首要问题，不是可以放在「后续优化」里的次要项。

其次是工程层面的边界：SQLite 单实例、Docker 只做了配置校验未实测运行、
没有概率校准、数据集规模小且缺少患者级标识、没有临床验证与医疗器械认证。

我倾向于把这些写进 README 的 Limitations，而不是只留在脑子里——写出来才说明自己清楚边界在哪。

## Q13b 外部评测集是均衡的，放到真实人群里这个模型会怎样？

这是我认为**最该被追问**的一点，而且结论对这个项目不利，所以要主动说：

外部评测集是 400 良性 / 397 恶性的均衡集合，而真实筛查场景的患病率远低于 50%。
按实测工作点（敏感度 65.49%、特异度 91.50%）换算：

| 患病率 | PPV | NPV | 每 1000 人漏检 | 每 1000 人误报 |
| ---: | ---: | ---: | ---: | ---: |
| 1% | 7.2% | 99.6% | 3.5 | 84.1 |
| 5% | 28.9% | 98.1% | 17.3 | 80.7 |
| 20% | 65.8% | 91.4% | 69.0 | 68.0 |
| 50%（评测集） | 88.5% | 72.6% | 172.5 | 42.5 |

也就是说：78.54% 这个准确率只在均衡集合上成立；患病率降到 1% 时，被判为「恶性倾向」的人里
只有约 7% 真的恶性，同时每 1000 人还会漏掉约 3.5 例恶性。
**结论是它不能作为独立筛查或排除手段，只能作为补充参考信号**——
这也是我在 README 与评测页里不写「筛查工具」的原因。换算脚本：`scripts/prevalence_analysis.py`。

## Q14 如果做 V2，你会怎么优化？

按优先级：

1. **解决泛化**：引入多来源、多设备的皮肤病变数据；获取患者/病灶级元数据改用患者级划分；
   重新训练时做域增强，并在新的独立数据上验证（不能用这次的外测数据当测试集）。
2. **概率校准**：做 temperature scaling 或 isotonic 校准，让置信度有实际解释力；
   医学语境下再考虑按敏感性优先选择工作点，并在验证集上完成、记录全过程。
3. **可解释性**：加入 Grad-CAM 之类的可视化，让使用者看到模型关注的区域，
   也便于排查「模型是不是在看背景而不是病灶」。
4. **工程扩展**：把 SQLite 换成 PostgreSQL，补上推理端点的配额与限流，
   真正跑通 Docker 构建与运行，并加托管 CI 把现有测试自动化。
5. **产品闭环**：增加用户反馈入口，用于收集误判样本（在合规与知情前提下）。

## 可能的追问

| 追问 | 回答要点 |
| --- | --- |
| 数据集从哪来？有授权吗？ | 训练数据由项目方提供（1840 张、benign/malignant 两目录）。仓库**不包含**数据集与图片，只保留划分清单与统计结果，因为再分发授权未确认。 |
| 为什么不用更大的模型/更强 backbone？ | 数据规模（1840 张）不支持更大容量，且过拟合趋势已经明显（训练 99.15% vs 验证 91–92%）。当前瓶颈是数据与域差异，不是模型容量。 |
| 为什么不直接用现成的皮肤 AI 服务？ | 项目的目标是完整实现 AI 应用的工程链路（含隐私与安全设计），调用外部 API 会跳过后端、存储与权限这些关键环节。 |
| 前端怎么保证不伪造结果？ | 前端不计算任何预测，只渲染后端返回的倾向、概率与模型版本；组件测试断言必须显示免责声明与「置信度不等于临床概率」。 |
| 你怎么知道线上服务用的就是训练好的模型？ | 真实模型冒烟脚本会比对 API 返回概率与本地加载同一 checkpoint 的前向结果（差 < 1e-4），并校验 model_version 不等于 stub。 |
