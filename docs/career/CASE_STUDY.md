# Case Study: 从 92.96% 到 78.54%

> 一份关于「内部指标好看、外部数据打脸」的真实 ML 工程复盘。所有数字来自仓库中的 artifact。

## Problem

皮肤病变的良恶性判断依赖专科医生读图，而专科医生资源有限，大规模早期筛查难以铺开。
项目要回答的问题很具体：**能不能让普通用户上传一张皮肤病变照片，就得到一个良恶性倾向提示，
并且这个提示背后有一条可追溯、可复核、不乱说话的工程链路。**

这个问题的难点不在「训一个二分类模型」——ResNet 迁移学习在 1000 多张图上很快就能跑到 90% 以上。
难点在于：模型到底能不能用在新数据上？产品怎么在不制造误导的前提下把结果交给用户？
以及一个 94 MB 的模型怎么变成一个别人能启动、能测试、能复核的系统。

## Constraints

- **数据条件受限**：1840 张（benign 1040 / malignant 800），无 patient_id / lesion_id，
  无法做患者级划分，只能做图像级分组划分。
- **不能造假**：不能把测试集回流训练、不能为了指标好看调阈值、不能把内部成绩当泛化结论。
- **医疗语境**：输出措辞必须避免「确诊」「临床级」这类表述，且要有常驻免责声明——
  这是产品要求，也是伦理要求。
- **单机交付**：需要在没有 GPU 集群、没有云服务的条件下交付一个能真实运行的系统（Windows 一键启动）。

## Approach

1. **先审计再设计**：扫描全部图片，统计类别/格式/尺寸，检测损坏文件，
   计算 SHA256 与 dHash，识别完全重复（1 组）与近似重复（24 组 / 62 张）。
2. **反泄漏划分**：把重复与近似重复的图片用并查集聚成「泄漏组」，整组分配到同一个划分，
   再做按类分层抽样（seed 42），最后断言 train/val/test 两两之间在 SHA256、组 key、
   类内文件名三个维度上的交集都是 0。产物：train 1294 / val 276 / test 270 + 划分清单 CSV。
3. **训练**：ResNet50 + ImageNet 预训练，两阶段迁移学习（先冻结 backbone 训分类头 3 epoch，
   再整体微调），类别权重、增强、混合精度、验证集 ROC-AUC 选模型、早停 patience=5。
   训练过程写出完整元数据（版本、种子、超参、环境、GPU）。
4. **把模型变成服务**：FastAPI 服务化，模型进程内单例加载；训练/评估/服务共用同一份预处理实现，
   均值方差从 checkpoint 读回，避免训练-服务漂移；推理并发上限 + 超时保护；
   模型版本随每条记录落库。
5. **把服务变成产品**：注册登录、上传检测、结果可视化、历史档案、双记录对比、CSV 导出、
   账号管理；每张图片真实解码、剥离 EXIF、Fernet 加密落盘，越权一律 404。
6. **验证**：内部测试集一次性评估；再用外部提供的 797 张独立图片做冻结模型评测，
   并用独立脚本从预测结果重算全部指标。

## Key Engineering Decisions

| 决策 | 理由 | 代价 / 边界 |
| --- | --- | --- |
| 图像级 group-aware 划分而非患者级 | 数据集中没有患者标识，这是能做到的最好方案 | 内部指标仍可能偏乐观，必须显式声明 |
| 测试划分只评估一次 | 保证它是「留出」的，不被反复调参污染 | 无代码强制机制，靠流程纪律与文档记录 |
| 训练/评估/服务共用同一 transform | 预处理漂移是这类项目最隐蔽的 bug 来源 | 服务端必须能读到 checkpoint 里的均值方差 |
| 模型单例 + 信号量限流 | 单机部署，避免重复加载与并发打爆 | 多 worker 部署时每个进程各加载一次 |
| 图像加密 + 服务端生成文件名 | 皮肤图像属敏感数据，文件名不可由客户端控制 | 加解密开销；密钥管理成为运维要求 |
| 保留外部测试集的真实结果，不重训不调阈值 | 一旦用测试集调参，它就不再是独立证据 | 交付的指标不好看，但可信 |

## Evaluation

| 指标 | 内部测试集 (n=270) | 独立外部测试集 (n=797) |
| --- | ---: | ---: |
| Accuracy | 92.96% | **78.54%** |
| Recall（恶性） | 93.97% | **65.49%** |
| Specificity | 92.21% | 91.50% |
| Precision（恶性） | 90.08% | 88.44% |
| F1 | 91.98% | 75.25% |
| ROC-AUC | 0.9828 | 0.9079 |
| PR-AUC | 0.9797 | 0.8929 |
| 混淆矩阵 | TP 109 / TN 142 / FP 12 / FN 7 | TP 260 / TN 366 / FP 34 / **FN 137** |

外部评测前确认与训练/验证/内部测试集的 SHA256 重合为 **0 / 0 / 0**；
评测脚本只做前向推理；指标由独立脚本重算并逐项比对通过（7/7）；
评测前后模型 SHA256 一致（`9c385625…d164e8`）。

## Unexpected Result

**内部 92.96% 的模型，在外部数据上只有 78.54%，而下降几乎全部集中在恶性召回上。**

这个结果最初看起来像「阈值偏保守」，但三条证据否定了这个解释：

1. 特异性基本没动（92.21% → 91.50%）——如果只是判定更保守，特异性应当明显上升；
2. 阈值扫描显示，把阈值压到 0.05，外部准确率也只到 83.56%，而特异性掉到 77%——
   换取召回的成本高得离谱；
3. Brier（0.057 → 0.167）与 ECE（0.043 → 0.151）同时大幅变差——
   模型在外部数据上不只是判断偏移，而是**置信度本身失真**了。

结论是：这不是决策阈值问题，而是模型在外部数据分布上的判别力确实下降了，
且下降对恶性样本影响最大。137 例恶性被判为良性，在筛查语境下是必须正面承认的风险。

更重要的是：**我没有对原因下结论。** 外部数据没有采集设备、患者来源、病灶级元数据，
分布差异只是可能因素之一。写「已证明是 domain shift」会让复盘看起来更完整，
但那是编故事，不是工程结论。

## What I Learned

1. **内部指标不是成绩，只是过程量。** 真正决定项目可信度的是「有没有用没见过的数据验证过」，
   以及验证结果不好时有没有如实保留。
2. **反泄漏要落到代码与断言上。** 「我们分了组」是声明；「划分后断言三重交集为 0 + 外部逐张 SHA256 比对」
   才是证据。
3. **AI 应用的工作量大头在产品与安全，不在模型。** 服务化、权限、加密、历史数据、错误处理、
   上传防护，这些决定了系统能不能真的被人使用。
4. **诚实是有工程成本的，也是要设计的。** 免责声明要常驻、禁用词要写成测试断言、
   指标要双口径展示、未实测项要显式标注 NOT TESTED——这些都需要主动设计，而不是靠自觉。
5. **AI Coding Agent 能放大产出，也会放大错误。** 它写出过引用不存在的 npm 脚本、
   把 dHash 写成 aHash 这类问题；流程里必须包含代码审查、真实运行验证与声明审计。

## What I Would Improve

| 方向 | 具体做法 | 预期收益 |
| --- | --- | --- |
| 泛化能力（首要） | 引入多来源多设备数据与患者/病灶元数据，改患者级划分；重训时做与外部条件匹配的域增强，并在**新的**独立数据上验证 | 提升外部准确率与恶性召回 |
| 概率校准 | temperature scaling / isotonic 校准，让置信度可解释；医学语境下按敏感性优先选工作点并记录全过程 | 降低「高置信度误判」的风险 |
| 可解释性 | 加入 Grad-CAM 可视化，检查模型是否在关注病灶区域而非背景 | 定位系统性错误，辅助排查数据问题 |
| 评估设计 | 按来源/设备分层评测，做交叉验证，补 bootstrap 置信区间 | 把「差距」拆成可归因的部分 |
| 工程扩展 | PostgreSQL 替换 SQLite、推理端点配额、真实跑通 Docker、托管 CI 自动化现有测试 | 从单机演示走向可维护部署 |
| 产品闭环 | 在合规前提下收集用户反馈与误判样本 | 形成数据驱动的迭代循环 |

一项实验纪律必须写在这里：**这次用于评测的 797 张图片已经用于评估。
如果将来基于这批数据做训练、参数选择或阈值调整，它就不能再作为未见过的测试集，
必须另外准备新的独立数据。** 本次 78.54% 应作为 V1 冻结模型的首次外部评测结果永久保留。
